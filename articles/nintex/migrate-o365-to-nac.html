Migrating Nintex for Office 365 to Nintex Automation Cloud – A Complete Playbook

A field-tested approach to moving Nintex for Office 365 workflows and forms to NAC, covering inventory, the Nintex migration tool, action mapping, redesigning list-bound workflows, rebuilding forms, connections, in-flight instances, testing, cut-over and lessons learned.

Moving from Nintex for Office 365 (O365) to Nintex Automation Cloud (NAC) is not a copy-paste job. O365 workflows are bound to a list, and NAC workflows are independent and connector-based. The best migrations combine tool-assisted conversion with targeted redesign.

#The playbook

#1 · Inventory and rationalize

Capture for each workflow: site, list, start type (manual, on create, on change), actions used, forms, last run date, run frequency, owner and business criticality.

Category Typical share Action
Not run in 12 months 20–40% Retire after owner confirmation
Simple notifications 20–30% Rebuild quickly in NAC (or SharePoint rules / Power Automate, if strategy allows)
Standard approvals 30–40% Tool conversion + adjust tasks and forms
Complex (state machines, loops, web requests, DocGen) 10–20% Redesign using NAC patterns (branch by stage, component workflows, Xtensions)

#2 · Prepare NAC

  • Connections: SharePoint Online connection on a service account with access to the target sites. Office 365 / Teams connections for notifications.
  • Naming convention: [Dept] – [Process] – [Trigger], for example QA – Deviation approval – Form.
  • Permissions: workflow owners and designers per department; connection usage rights.
  • Component workflows for shared pieces: approver resolution, audit logging, notifications.

#3 · Convert with the migration tool, then fix

Nintex provides migration tooling to export O365 workflows and import them into NAC, producing a conversion report that lists unsupported actions. Expect to fix:

O365 element NAC approach
Start on item created/modified SharePoint Online start event (watch for duplicate triggers), or a NAC form as start
Workflow context (Current item) Start event variables; Get item action to refresh fields
Request approval / Flexi task Assign a task (custom outcomes) / Express approval
Task forms (O365) NAC task forms
Set a condition / Run if Branch by condition
State machine Branch by stage
Loop / For each Loop for each / Loop condition
Web request / Call HTTP web service Call a web service or Xtension
Query list (CAML) SharePoint Query a list (filters)
Office 365 actions (create site, user) Microsoft 365 / Graph via Xtension
Workflow history logging Instance history + explicit audit list item

#4 · Rebuild forms

Nintex Forms for Office 365 (classic/responsive) are rebuilt as NAC forms:

  • Recreate rules (show/hide, validation) with NAC rules.
  • Replace JavaScript with built-in features or custom plugins.
  • Convert repeating section XML into collections and a child list in SharePoint.
  • Decide the entry point: NAC form as the start (recommended), or keep data entry in SharePoint (list form or Power Apps) and start the workflow on item events.

#5 · In-flight instances and cut-over

  • Announce a freeze date: no new O365 instances after cut-over.
  • Let short in-flight instances finish. For long ones, migrate status into list columns and start NAC workflows at the right stage (Branch by stage with an entry variable).
  • Turn off O365 workflow start options, then publish NAC workflows.
  • Monitor NAC instances closely for 2 weeks (hypercare).
Lessons from real migrations
  • Retire aggressively. Many workflows are unused.
  • Standardize approval patterns into one or two component workflows. It cuts build time dramatically.
  • Fix data quality (people fields, choices) before go-live, because NAC is stricter with types.
  • Document each migrated workflow with a one-page design (trigger, stages, tasks, connections) in a System Understanding Document.
  • Train approvers on the new task experience (email, mobile, NAC task list).

#Interview questions

Q1What is the biggest design difference when migrating from Nintex for Office 365 to NAC?

O365 workflows are bound to a list and run with the list item as context. NAC workflows are independent and connect to SharePoint through connectors and start events. You must handle item context explicitly (start event variables, Get item), connections, and often redesign start mechanisms and forms.

Q2How do you handle long-running in-flight instances during migration?

Freeze new starts, let short instances finish, and for long ones persist their current state (status, approvers, comments) on the item and start the NAC workflow at the matching stage using Branch by stage with an entry variable. Then terminate the old instances.

Q3What would you put in the migration inventory?

Site and list, workflow name, trigger type, actions used (especially unsupported ones), forms and scripts, last run and frequency, number of running instances, owner, business criticality, dependencies (web services, DocGen) and the target decision (retire, convert, redesign).
