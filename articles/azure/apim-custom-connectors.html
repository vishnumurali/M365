Azure API Management for Microsoft 365 Solutions – Securing and Publishing APIs to Power Platform

Use APIM as the front door for your APIs, covering products and subscriptions, validate-jwt for Entra tokens, rate limits, caching, transforming legacy SOAP to REST, exporting APIs directly to Power Platform as custom connectors, and versioning.

APIM inbound policy: require Entra token with a role, throttle per callerXML
<inbound>
  <base />
  <validate-jwt header-name="Authorization" failed-validation-httpcode="401" require-scheme="Bearer">
    <openid-config url="https://login.microsoftonline.com/{tenant-id}/v2.0/.well-known/openid-configuration" />
    <audiences><audience>api://deviation-api</audience></audiences>
    <required-claims>
      <claim name="roles" match="any"><value>Deviations.Read</value><value>Deviations.ReadWrite</value></claim>
    </required-claims>
  </validate-jwt>
  <rate-limit-by-key calls="120" renewal-period="60" counter-key="@(context.Request.Headers.GetValueOrDefault("Authorization","").AsJwt()?.Subject)" />
  <cache-lookup vary-by-developer="false" vary-by-developer-groups="false" />
</inbound>

#Publishing to Power Platform

APIM can export an API to a Power Platform environment as a custom connector (APIM → API → Create Power Connector), with authentication settings. Makers then use typed actions without knowing the backend.

#Interview questions

Q1Why put APIM in front of Azure Functions used by Power Platform?

Central security (JWT validation, IP filters), rate limiting and quotas per consumer, caching, transformation, versioning, monitoring and a developer portal, plus one-click export to Power Platform as a custom connector.

Q2What does the validate-jwt policy do?

It validates the bearer token's signature, issuer, audience, expiry and required claims (scopes or roles) against Entra ID's OpenID configuration before the request reaches the backend, and rejects invalid calls with 401.
