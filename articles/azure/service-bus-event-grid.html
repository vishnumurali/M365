Service Bus vs Event Grid vs Storage Queues – Messaging Patterns for M365 Integrations

Choose the right messaging service, covering queues vs topics, Event Grid events and system topics, Storage queues for simple buffering, retries, dead-lettering, idempotency and ordering, with SharePoint, Dataverse and Graph examples.

Service Model Best for
Storage Queues Simple queue Cheap buffering (webhook → processor), < 64 KB messages
Service Bus queues Brokered messaging Commands, ordered processing (sessions), transactions, dead-letter
Service Bus topics Pub/sub One event, many subscribers with filters (Dataverse → ERP + DWH)
Event Grid Reactive events "Something happened" (blob created, Graph/partner events) fan-out via push
Event Hubs Streaming Telemetry at massive scale

#Reliability rules

  • Idempotent consumers: messages can be delivered more than once (at-least-once).
  • Dead-letter queues: inspect and replay poison messages; alert on DLQ depth.
  • Retries with backoff: Functions bindings retry, so set max delivery counts.
  • Ordering: use Service Bus sessions when per-entity order matters.

#Interview questions

Q1When would you use Service Bus instead of a Storage queue?

When you need topics/subscriptions (pub/sub), ordered processing (sessions), duplicate detection, transactions, scheduled messages, larger messages or richer dead-letter handling. Storage queues are fine for simple, cheap buffering.

Q2What is the difference between Event Grid and Service Bus?

Event Grid distributes lightweight events (notifications that something happened) to many handlers with push delivery. Service Bus is a message broker for commands and business messages with queues, ordering, sessions and transactional guarantees.
