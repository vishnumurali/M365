How to Write a High-Level Design (HLD) – Template and Full Example for a SharePoint + Power Platform Solution

A complete HLD guide, covering purpose and audience, architecture overview diagrams, component inventory, data architecture and platform choice, integration, security and identity, licensing, ALM and environments, NFRs, risks and decisions (ADRs), with a worked Deviation Management System HLD.

The High-Level Design (HLD) explains how the solution will be built at the architecture level: the main components, where data lives, how pieces communicate, and how security, licensing and deployment work. Its audience is architects, security, platform owners, the delivery team and technical stakeholders.

#Worked example: Deviation Management System (DMS)

#3 · Component inventory

ID Component Technology Responsibility
C1 DMS app Power Apps canvas (responsive) Report, view, update deviations
C2 DMS Admin Model-driven app QA administration, CAPA, master data
C3 Approval flows Power Automate (solution) Manager/QA approvals, reminders, escalations
C4 Evidence library SharePoint Online Photos, documents per deviation (folder per record)
C5 Report generator Azure Function (.NET 8) Monthly PDF per plant to SharePoint
C6 Dashboard SPFx web part + Power BI Intranet KPIs

#4 · Data architecture & key decision

ADR-01: Dataverse instead of SharePoint lists

Context: 12k deviations/year, relational data (CAPA, approvals), plant-level security, 10-year audit. Options: SharePoint lists, Dataverse, Azure SQL. Decision: Dataverse (row-level security via BUs per plant, auditing, model-driven admin, no list thresholds). Consequences: Power Apps premium licences for 1,500 users; documents remain in SharePoint (cost-effective storage).

#6 · Security model

Role Access
Reporter Create; read own deviations
Plant QA Read/write deviations of their plant (BU)
Area manager Approve deviations in their area
QA Central Read/write all plants
Auditor Read-only all, including audit history

Identity: Entra ID SSO; Dataverse security roles assigned through Entra group teams; SharePoint evidence library permissions mirrored by plant groups; flows run with a service account connection.

#Reviewer checklist

  • Every BRD requirement maps to a component
  • Data store choice justified (ADR)
  • Security model covers all roles and NFRs
  • Licensing calculated per persona
  • Integration error handling defined
  • ALM and environments defined
  • Monitoring and support model described

#Interview questions

Q1What belongs in an HLD vs an LLD?

The HLD covers architecture: components, platforms, data stores and why, integrations, security model, licensing, environments and ALM, and NFR approach. The LLD covers implementation detail per component: schemas, columns and types, screens and controls, flow steps, formulas, API contracts, naming and configuration values.

Q2What is an ADR and why include it in an HLD?

An Architecture Decision Record captures a significant decision: its context, the options considered, the decision and its consequences. ADRs prevent re-litigating decisions and help future maintainers understand why the solution looks the way it does.
