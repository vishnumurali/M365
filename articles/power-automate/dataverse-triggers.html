Dataverse in Power Automate – Triggers, Filtering Rows, Actions and Bound/Unbound Actions

Automate Dataverse with 'When a row is added, modified or deleted' (scope, select columns, filter rows), list rows with FetchXML and OData, relate rows, perform bound and unbound actions, and compare flows with plug-ins.

#The trigger, configured well

Setting Use
Change type Added, Modified, Deleted (or combinations)
Table e.g. Deviations
Scope User / Business unit / Parent-child BU / Organization
Select columns ci_status,ci_severity, which fires only when these columns change (prevents loops)
Filter rows OData: ci_severity eq 100000002 and statecode eq 0
Run as (in solutions) Flow owner / modifying user / row owner

#List rows: OData or FetchXML

OData in 'List rows'Text
Select columns:  ci_name,ci_duedate,_ci_plant_value
Filter rows:     statecode eq 0 and ci_duedate lt @{utcNow()}
Sort by:         ci_duedate asc
Expand Query:    ci_Plant($select=ci_name)
Row count:       5000   (+ pagination for more)
FetchXML (aggregates, linked entities)XML
<fetch aggregate="true">
  <entity name="ci_deviation">
    <attribute name="ci_deviationid" alias="count" aggregate="count" />
    <attribute name="ci_severity" alias="severity" groupby="true" />
    <filter><condition attribute="statecode" operator="eq" value="0" /></filter>
  </entity>
</fetch>

#Flows vs plug-ins

Power Automate Plug-in (C#)
Timing Asynchronous (seconds later) Synchronous or async, in transaction
Can block the save ❌ ✅ (throw InvalidPluginExecutionException)
Skill Maker Developer
Integration with other services ✅ connectors Limited (HTTP from sandbox)
Best for Notifications, integrations, approvals Validation, calculations that must be atomic

#Interview questions

Q1How do you stop a Dataverse-triggered flow from looping when it updates the same row?

Set Select columns on the trigger to only the columns that should start the flow, excluding the columns the flow updates, and/or add Filter rows so the flow ignores rows already processed.

Q2When should you use a plug-in instead of a flow?

When logic must run synchronously inside the transaction, for example to block an invalid save, guarantee consistency across rows, or calculate values before commit. Flows run asynchronously after the change.
