Service Applications – Architecture, Proxies & the Full Catalog

How SharePoint shares services such as Search, Managed Metadata and User Profiles across web applications, covering the service app, proxy and proxy group model, plus a catalog of every major service and how to provision it with PowerShell.

SharePoint 2010 replaced the old Shared Services Provider (SSP) of MOSS 2007 with service applications. These are independent, shareable services that web applications consume through proxies. The model is still the same in Subscription Edition.

#How the pieces connect

  • A service application is the logical service plus its configuration, app pool and database(s).
  • A service instance is the service actually running on a server. MinRole starts instances automatically.
  • A proxy is how a web application talks to a service application.
  • A proxy group is a named set of proxies that you associate with web applications. That is how you give an extranet a different set of services than the intranet.

#The catalog

#Provisioning a service application with PowerShell

Central Administration wizards create databases with GUIDs in their names and run every service under one account. Professionals script service apps instead:

Managed Metadata Service with a dedicated app poolPowerShell
Add-PSSnapin Microsoft.SharePoint.PowerShell -ErrorAction SilentlyContinue

$poolName = "SharePoint Services App Pool"
$pool = Get-SPServiceApplicationPool -Identity $poolName -ErrorAction SilentlyContinue
if (-not $pool) {
  $pool = New-SPServiceApplicationPool -Name $poolName -Account (Get-SPManagedAccount "CONTOSO\sp_services")
}

$mms = New-SPMetadataServiceApplication -Name "Managed Metadata Service" `
          -ApplicationPool $pool -DatabaseName "SP_Service_MMS" `
          -DatabaseServer "SQLAG-LISTENER"

New-SPMetadataServiceApplicationProxy -Name "Managed Metadata Service Proxy" `
          -ServiceApplication $mms -DefaultProxyGroup -ContentTypePushdownEnabled -DefaultKeywordTaxonomy -DefaultSiteCollectionTaxonomy

# Make sure the instance is running somewhere (MinRole does this for compliant roles)
Get-SPServiceInstance | Where-Object TypeName -eq "Managed Metadata Web Service" |
  Select-Object Server, Status
Secure Store and its master keyPowerShell
$ss = New-SPSecureStoreServiceApplication -Name "Secure Store" -ApplicationPool $pool `
        -DatabaseName "SP_Service_SecureStore" -AuditingEnabled
$ssp = New-SPSecureStoreServiceApplicationProxy -Name "Secure Store Proxy" -ServiceApplication $ss -DefaultProxyGroup

# The master key encrypts credentials. Store the passphrase in your vault, because you need it for DR!
Update-SPSecureStoreMasterKey -ServiceApplicationProxy $ssp -Passphrase $passphrase
Start-Sleep 5
Update-SPSecureStoreApplicationServerKey -ServiceApplicationProxy $ssp -Passphrase $passphrase

#Custom proxy groups (e.g. extranet without profiles)

Give the extranet only Search + MMSPowerShell
$pg = New-SPServiceApplicationProxyGroup -Name "Extranet Proxy Group"
Add-SPServiceApplicationProxyGroupMember $pg -Member (Get-SPServiceApplicationProxy | Where-Object Name -like "*Search*")
Add-SPServiceApplicationProxyGroupMember $pg -Member (Get-SPServiceApplicationProxy | Where-Object Name -like "*Managed Metadata*")

Set-SPWebApplication -Identity "https://partners.contoso.com" -ServiceApplicationProxyGroup $pg

#Cross-farm service sharing

Large enterprises sometimes run a central services farm that publishes Search, MMS, UPS and Secure Store to several consumer farms:

This requires exchanging root and STS certificates (New-SPTrustedRootAuthority, New-SPTrustedServiceTokenIssuer), publishing the service app (Publish-SPServiceApplication), and connecting with New-SP*ServiceApplicationProxy -Uri. It saves resources but couples farm patch levels, so most organizations avoid it unless they have scale reasons.

#Troubleshooting checklist

Symptom Check
"The service application is not available" Is the service instance started on any server? Is the proxy in the web app's proxy group?
Term store greyed out MMS app pool account needs Full Control on the MMS (Permissions dialog); the proxy needs "default storage location"
Profiles not updating AD import connection, sync account "Replicate Directory Changes" permission, timer job history
Secure Store errors after DR Master key passphrase not applied in the DR farm
Slow page loads after patch App pools recycled, service app endpoints warming up; check ULS for WCF timeouts

#Interview questions

Q1What is the difference between a service application, a service instance and a proxy?

The service application is the logical, configured service with its databases and app pool. A service instance is that service running on a specific server. A proxy is the client-side connector that web applications use to call the service application. Proxies are grouped into proxy groups and associated with web applications.

Q2How can you prevent an extranet web application from using the User Profile service?

Create a custom proxy group that contains only the required proxies (for example Search and MMS) and associate the extranet web application with that group instead of the default proxy group.

Q3Why script service applications instead of using the Farm Configuration Wizard?

Scripts give predictable database names (no GUIDs), dedicated least-privilege accounts and app pools, repeatability across dev, test and prod, and a record of the configuration for DR rebuilds.
