Remote Event Receivers (RER) – How They Work, Code & Retirement

How SharePoint calls out to a remote WCF service when list, item or add-in events fire, with sync vs async handling, registration, full C# code, and the modern webhook replacement.

A remote event receiver (RER) is an event handler whose code does not run inside SharePoint. When something happens in a list, library, web or add-in, SharePoint makes a SOAP call to a web service you host (on IIS or Azure App Service) and passes the event details. Your service reacts: it can validate data and cancel the change, update other items, call other systems, or log.

RERs arrived with the SharePoint 2013 add-in (app) model. Microsoft wanted custom code out of the SharePoint process (farm solutions) so SharePoint Online could stay stable, and RERs were the answer for event-driven logic.

Where RERs sit in the timeline

2007–2010: classic event receivers ran inside w3wp.exe as farm or sandboxed code. 2013: RERs moved that code to remote web services. 2016+: SharePoint webhooks became the recommended pattern for SharePoint Online. April 2, 2026: SharePoint Add-ins and Azure ACS were retired in SharePoint Online, so ACS-based RERs there stopped working. On-premises (2016, 2019, Subscription Edition), RERs still work with high-trust (S2S) add-ins.

#How a remote event receiver works

The flow:

  1. A user (or code) changes an item in a list that has an RER registered on it.
  2. SharePoint's event pipeline finds the registration and sees a ReceiverUrl pointing at your .svc endpoint.
  3. SharePoint serializes the event into SPRemoteEventProperties: event type, list ID, item ID, before and after properties, and a context token. It then POSTs that object to your service.
  4. Your service implements IRemoteEventService:
    • ProcessEvent for synchronous ("-ing") events. SharePoint waits for your response, which can cancel the operation or change field values.
    • ProcessOneWayEvent for asynchronous ("-ed") events. SharePoint fires and forgets.
  5. If you need to read or write SharePoint, TokenHelper.CreateRemoteEventReceiverClientContext(properties) turns the context token into an access token and gives you a CSOM ClientContext.

#Writing the receiver (C#)

Create a provider-hosted add-in in Visual Studio (2013 to 2019 templates). Then use Add → New Item → Remote Event Receiver. Visual Studio generates a .svc file, a class that implements IRemoteEventService, and an Elements.xml registration.

Services/DeviationReceiver.svc.csC#
using System;
using Microsoft.SharePoint.Client;
using Microsoft.SharePoint.Client.EventReceivers;

namespace Contoso.DeviationsWeb.Services
{
    public class DeviationReceiver : IRemoteEventService
    {
        // SYNCHRONOUS: runs BEFORE the change is committed. Can cancel or modify.
        public SPRemoteEventResult ProcessEvent(SPRemoteEventProperties properties)
        {
            var result = new SPRemoteEventResult { Status = SPRemoteEventServiceStatus.Continue };

            switch (properties.EventType)
            {
                case SPRemoteEventType.ItemAdding:
                case SPRemoteEventType.ItemUpdating:
                    var after = properties.ItemEventProperties.AfterProperties;
                    var title = after.ContainsKey("Title") ? after["Title"] as string : null;

                    if (string.IsNullOrWhiteSpace(title) || title.Trim().Length < 5)
                    {
                        result.Status = SPRemoteEventServiceStatus.CancelWithError;
                        result.ErrorMessage = "Deviation title must be at least 5 characters.";
                        return result;
                    }
                    // Stamp a value before it is saved (no extra round trip needed)
                    result.ChangedItemProperties.Add("Status", "Submitted");
                    break;

                case SPRemoteEventType.ItemDeleting:
                    result.Status = SPRemoteEventServiceStatus.CancelWithError;
                    result.ErrorMessage = "Deviations cannot be deleted. Close them instead.";
                    break;
            }
            return result;
        }

        // ASYNCHRONOUS: runs AFTER the change. Fire-and-forget, cannot cancel.
        public void ProcessOneWayEvent(SPRemoteEventProperties properties)
        {
            if (properties.EventType != SPRemoteEventType.ItemAdded) return;

            using (ClientContext ctx = TokenHelper.CreateRemoteEventReceiverClientContext(properties))
            {
                if (ctx == null) return; // token could not be issued (check trust / ACS)

                var props = properties.ItemEventProperties;
                List audit = ctx.Web.Lists.GetByTitle("DeviationAudit");
                ListItem log = audit.AddItem(new ListItemCreationInformation());
                log["Title"] = $"Deviation {props.ListItemId} created";
                log["DeviationId"] = props.ListItemId;
                log["CreatedBy"] = props.UserLoginName;
                log.Update();
                ctx.ExecuteQuery();
            }
        }
    }
}
DeviationReceiver/Elements.xml (declarative registration)XML
<?xml version="1.0" encoding="utf-8"?>
<Elements xmlns="http://schemas.microsoft.com/sharepoint/">
  <!-- ListTemplateId 100 = Custom List. Declarative RERs bind to lists in the ADD-IN WEB. -->
  <Receivers ListTemplateId="100">
    <Receiver>
      <Name>DeviationItemAdding</Name>
      <Type>ItemAdding</Type>
      <SequenceNumber>10000</SequenceNumber>
      <Url>~remoteAppUrl/Services/DeviationReceiver.svc</Url>
    </Receiver>

  </Receivers>
</Elements>

#Registering an RER on a host-web list

Declarative Elements.xml registrations attach only to lists in the add-in web. Most real solutions need the receiver on a list in the host web (the user's site). To do that, handle AppInstalled and register the receiver with CSOM:

Services/AppEventReceiver.svc.csC#
public SPRemoteEventResult ProcessEvent(SPRemoteEventProperties properties)
{
    var result = new SPRemoteEventResult();
    const string receiverName = "DeviationItemAdded";

    using (ClientContext ctx = TokenHelper.CreateAppEventClientContext(properties, useAppWeb: false))
    {
        if (ctx == null) return result;
        List list = ctx.Web.Lists.GetByTitle("Deviations");
        ctx.Load(list.EventReceivers);
        ctx.ExecuteQuery();

        if (properties.EventType == SPRemoteEventType.AppInstalled)
        {
            // Build the receiver URL from the URL this service was called on
            string svcUrl = System.ServiceModel.OperationContext.Current.Channel.LocalAddress.Uri.AbsoluteUri
                                .Replace("AppEventReceiver.svc", "DeviationReceiver.svc");

            bool exists = list.EventReceivers.Any(r => r.ReceiverName == receiverName);
            if (!exists)
            {
                list.EventReceivers.Add(new EventReceiverDefinitionCreationInformation
                {
                    EventType = EventReceiverType.ItemAdded,
                    ReceiverName = receiverName,
                    ReceiverUrl = svcUrl,
                    SequenceNumber = 1000,
                    Synchronization = EventReceiverSynchronization.Asynchronous
                });
                ctx.ExecuteQuery();
            }
        }
        else if (properties.EventType == SPRemoteEventType.AppUninstalling)
        {
            // Clean up, otherwise SharePoint keeps calling a dead endpoint
            foreach (var r in list.EventReceivers.ToList().Where(r => r.ReceiverName == receiverName))
                r.DeleteObject();
            ctx.ExecuteQuery();
        }
    }
    return result;
}

You can also inspect and manage registrations from PowerShell, which helps a lot when cleaning up orphaned receivers before a migration:

Inspect / add / remove event receivers with PnP PowerShellPowerShell
Connect-PnPOnline -Url "https://contoso.sharepoint.com/sites/quality" -Interactive -ClientId $clientId

# List every receiver on a list (look for ReceiverUrl pointing to retired add-in hosts)
Get-PnPEventReceiver -List "Deviations" | Select-Object ReceiverName, EventType, Synchronization, ReceiverUrl

# Register a receiver manually (on-prem high-trust scenarios / testing)
Add-PnPEventReceiver -List "Deviations" -Name "DeviationItemAdded" `
  -Url "https://apps.contoso.com/Services/DeviationReceiver.svc" `
  -EventReceiverType ItemAdded -Synchronization Asynchronous

# Remove an orphaned receiver
Get-PnPEventReceiver -List "Deviations" |
  Where-Object ReceiverName -eq "DeviationItemAdded" |
  ForEach-Object { Remove-PnPEventReceiver -List "Deviations" -Identity $_.ReceiverId -Force }
The infinite-loop trap

SSOM event receivers can call EventFiringEnabled = false. RERs cannot. If ItemUpdated updates the same item, it fires ItemUpdated again. Guard every update: compare the current value before writing, or write to a different list (as the audit example does).

#The modern replacement: webhooks + Azure Functions

For SharePoint Online the replacement pattern is a webhook subscription plus a small Azure Function. The function acknowledges the notification within 5 seconds, then queues the work. A second function calls GetChanges with a stored change token to find out what actually changed. The full implementation is in SharePoint webhooks with Azure Functions.

src/functions/spWebhook.ts (Azure Functions v4, Node)TypeScript
import { app, output, HttpRequest, HttpResponseInit, InvocationContext } from '@azure/functions';

const changesQueue = output.storageQueue({ queueName: 'sp-changes', connection: 'AzureWebJobsStorage' });

app.http('spWebhook', {
  methods: ['POST'],
  authLevel: 'function',
  extraOutputs: [changesQueue],
  handler: async (req: HttpRequest, ctx: InvocationContext): Promise<HttpResponseInit> => {
    // 1) Subscription handshake: echo the validation token (must answer within 5 seconds)
    const validationToken = req.query.get('validationtoken');
    if (validationToken) {
      return { status: 200, headers: { 'Content-Type': 'text/plain' }, body: validationToken };
    }

    // 2) Notification: payload only tells you WHICH list changed, not what changed
    const payload = (await req.json()) as { value: Array<{ subscriptionId: string; resource: string; siteUrl: string; clientState?: string }> };
    const valid = payload.value.filter(n => n.clientState === process.env.WEBHOOK_CLIENT_STATE);
    ctx.extraOutputs.set(changesQueue, valid);   // hand off and return fast
    return { status: 200 };
  },
});
Equivalent receiver in C# (isolated worker, multi-output)C#
public class WebhookOutput
{
    [QueueOutput("sp-changes")]
    public string[]? Messages { get; set; }      // each string becomes a queue message
    public HttpResponseData Response { get; set; } = default!;
}

[Function("SpWebhook")]
public async Task<WebhookOutput> Run(
    [HttpTrigger(AuthorizationLevel.Function, "post")] HttpRequestData req)
{
    var response = req.CreateResponse(HttpStatusCode.OK);

    // 1) Subscription handshake: echo validationtoken as plain text
    var token = System.Web.HttpUtility.ParseQueryString(req.Url.Query)["validationtoken"];
    if (!string.IsNullOrEmpty(token))
    {
        response.Headers.Add("Content-Type", "text/plain");
        await response.WriteStringAsync(token);
        return new WebhookOutput { Response = response };
    }

    // 2) Notification: validate clientState, queue, return 200 quickly
    var payload = await JsonSerializer.DeserializeAsync<WebhookPayload>(req.Body,
        new JsonSerializerOptions { PropertyNameCaseInsensitive = true });
    var messages = payload!.Value
        .Where(n => n.ClientState == Environment.GetEnvironmentVariable("WEBHOOK_CLIENT_STATE"))
        .Select(n => JsonSerializer.Serialize(n))
        .ToArray();
    return new WebhookOutput { Response = response, Messages = messages };
}

#Common problems and fixes

Symptom Likely cause Fix
Receiver never fires Registered on the add-in web instead of the host web; wrong ListTemplateId Register via AppInstalled + CSOM, then verify with Get-PnPEventReceiver
CreateRemoteEventReceiverClientContext returns null Missing or invalid context token, add-in lacks permission, clock skew, ACS retired Check AppManifest.xml permissions, server time, and the trust model (S2S on-prem)
Users see "Sorry, something went wrong" on save Sync receiver threw or timed out Wrap ProcessEvent in try/catch, return Continue on non-critical errors, and log
Duplicate processing Async event retried by the client, or the receiver is registered twice Make handlers idempotent; check for existing receivers before adding
Works in dev, fails in prod Endpoint not reachable from SharePoint (firewall, TLS, self-signed cert) Use a public HTTPS endpoint with a valid certificate; for on-prem allow SharePoint → app server traffic
Calls continue after uninstall Receivers were not removed in AppUninstalling Clean up in AppUninstalling or with PnP PowerShell
Migration checklist

Before you migrate a farm or tenant, inventory every event receiver that has a non-empty ReceiverUrl. Each one is a dependency on an external host that will not move with the content. In practice: on-prem RERs move to webhooks + Azure Functions; simple validations move to column / list validation formulas or Power Automate; and complex sync validation moves to an SPFx form customizer.

#Interview questions

Q1What is the difference between ProcessEvent and ProcessOneWayEvent?

ProcessEvent handles synchronous events (ItemAdding, ItemUpdating, AppInstalled and so on). SharePoint waits for the returned SPRemoteEventResult, which can cancel the operation (CancelWithError) or change values (ChangedItemProperties). ProcessOneWayEvent handles asynchronous "-ed" events after the change is committed. It returns void and cannot cancel.

Q2How do you attach a remote event receiver to a list in the host web?

Declarative Elements.xml registration targets the add-in web only. For host-web lists, handle the AppInstalled add-in event, create a ClientContext with TokenHelper.CreateAppEventClientContext(properties, false), and call list.EventReceivers.Add(new EventReceiverDefinitionCreationInformation { ... }). Remove the receiver in AppUninstalling.

Q3How do you prevent an infinite loop in an ItemUpdated RER?

RERs have no EventFiringEnabled switch. Compare the current value with the intended value before updating, use a marker field, or perform the update in the synchronous ItemUpdating through ChangedItemProperties, which does not cause a second event.

Q4Why were RERs replaced by webhooks in SharePoint Online?

RERs depend on the add-in model and Azure ACS for tokens, and both were retired in SPO on 2 April 2026. They also have no retry or delivery guarantee. Webhooks are standards-based HTTPS callbacks with retries and work with modern Entra ID app auth. Because the payload is minimal, you call GetChanges to fetch the details.

Q5Can a webhook cancel an item update like an -ing RER?

No. Webhooks are notification-only and asynchronous. For blocking validation in SPO, use column or list validation, required fields with conditional formulas, or a custom SPFx form customizer or Power Apps form that validates before saving.
