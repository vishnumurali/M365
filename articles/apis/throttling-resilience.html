Throttling & Resilience for SharePoint and Graph – 429s, Retry-After and Decorated Traffic

Build integrations that survive throttling, covering how SharePoint Online and Graph throttle (per user, per app, per tenant, resource units), handling 429/503 with Retry-After, exponential backoff, batching and delta to reduce calls, decorating traffic with a user agent, and monitoring.

SharePoint Online and Graph protect shared infrastructure by throttling: when a caller exceeds limits, they respond 429 Too Many Requests (or 503 Server Too Busy) with a Retry-After header. Well-behaved code waits and retries. Badly behaved code retries immediately and gets blocked longer.

#Limits to know (conceptually)

Scope What's measured
Per user Requests per time window
Per app (per tenant) Resource units per minute/day (SharePoint app throttling, weighted by operation cost)
Per tenant Overall load on the tenant's farm
Graph workloads Service-specific limits (e.g. Teams, Outlook, SharePoint via Graph)

Operations cost differently: a delta query or a single-item GET is cheap, while full-list scans, permission-heavy calls and searches are expensive.

#Resilient client (C#)

HttpClient handler honouring Retry-After with backoff and jitterC#
public class ThrottleRetryHandler : DelegatingHandler
{
    protected override async Task<HttpResponseMessage> SendAsync(HttpRequestMessage req, CancellationToken ct)
    {
        for (int attempt = 1; ; attempt++)
        {
            var res = await base.SendAsync(req, ct);
            if ((int)res.StatusCode is not (429 or 503) || attempt == 6) return res;

            TimeSpan wait = res.Headers.RetryAfter?.Delta
                ?? TimeSpan.FromSeconds(Math.Pow(2, attempt) + Random.Shared.NextDouble());
            await Task.Delay(wait, ct);
            req = await CloneAsync(req);   // HttpRequestMessage can't be resent as-is
        }
    }
}

#Interview questions

Q1What should your code do when it receives HTTP 429 from SharePoint Online?

Read the Retry-After header and wait at least that long before retrying the same request. Fall back to exponential backoff with jitter if the header is missing, and reduce the request rate. Never retry immediately in a tight loop.

Q2What is "decorating traffic" and why do it?

Setting a descriptive User-Agent (e.g. NONISV|Company|App/1.0 or ISV|Company|App/1.0) on requests. Microsoft uses it to identify and prioritize well-behaved applications during throttling.
