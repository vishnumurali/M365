SPFx CI/CD with Azure DevOps – YAML Pipeline to Build, Test, Package and Deploy

A production-ready Azure DevOps multi-stage YAML pipeline for SPFx, covering Node setup, npm ci with caching, lint and Jest tests, ship build, versioning, artifacts, certificate-based CLI for Microsoft 365 login, deployment to test and prod app catalogs with approvals.

Manual "build on my laptop and upload" deployments do not scale and cannot be audited. A pipeline makes every release repeatable, tested, versioned and approved.

#Pipeline design

#Prerequisites

  1. An Entra app registration for deployment with a certificate, granted SharePoint → Sites.FullControl.All (application) or, preferably, Sites.Selected with full control on the app catalog site.
  2. Upload the .pfx to Pipelines → Library → Secure files (spfx-deploy.pfx).
  3. A variable group spfx-deploy with TenantId, AppId, CertPassword (secret), AppCatalogUrl.
  4. Two Environments: spfx-test and spfx-prod (with approvers).

#The YAML

azure-pipelines.ymlYAML
trigger:
  branches: { include: [ main ] }
  tags: { include: [ 'v*' ] }
pr:
  branches: { include: [ main ] }

variables:
  - group: spfx-deploy
  - name: nodeVersion
    value: '22.x'
  - name: packageName
    value: 'deviation-webparts.sppkg'

stages:
- stage: Build
  jobs:
  - job: build
    pool: { vmImage: 'ubuntu-latest' }
    steps:
    - task: NodeTool@0
      inputs: { versionSpec: '$(nodeVersion)' }
      displayName: 'Use Node $(nodeVersion)'

    - task: Cache@2
      inputs:
        key: 'npm | "$(Agent.OS)" | package-lock.json'
        path: '$(Pipeline.Workspace)/.npm'
      displayName: 'Cache npm'

    - script: npm ci --cache $(Pipeline.Workspace)/.npm
      displayName: 'npm ci'

    - script: npm run lint && npm test -- --ci --reporters=default --reporters=jest-junit
      displayName: 'Lint & unit tests'

    - task: PublishTestResults@2
      condition: succeededOrFailed()
      inputs: { testResultsFiles: '**/junit.xml' }

    # Stamp the solution version from the pipeline run (e.g. 1.4.<run>.0)
    - pwsh: |
        $f = 'config/package-solution.json'
        $j = Get-Content $f -Raw | ConvertFrom-Json
        $parts = $j.solution.version.Split('.')
        $j.solution.version = "$($parts[0]).$($parts[1]).$(Build.BuildId).0"
        $j | ConvertTo-Json -Depth 20 | Set-Content $f
        Write-Host "Version: $($j.solution.version)"
      displayName: 'Stamp version'

    - script: |
        npx gulp bundle --ship
        npx gulp package-solution --ship
      displayName: 'Ship build & package'   # Heft-based versions: use the npm scripts from package.json

    - publish: sharepoint/solution/$(packageName)
      artifact: sppkg

- stage: DeployTest
  dependsOn: Build
  condition: and(succeeded(), ne(variables['Build.Reason'], 'PullRequest'))
  jobs:
  - deployment: test
    environment: spfx-test
    pool: { vmImage: 'ubuntu-latest' }
    strategy:
      runOnce:
        deploy:
          steps:
          - template: templates/deploy-steps.yml
            parameters: { appCatalogUrl: '$(TestAppCatalogUrl)', scope: 'sitecollection' }

- stage: DeployProd
  dependsOn: DeployTest
  condition: and(succeeded(), startsWith(variables['Build.SourceBranch'], 'refs/tags/v'))
  jobs:
  - deployment: prod
    environment: spfx-prod            # approvals configured on the environment
    pool: { vmImage: 'ubuntu-latest' }
    strategy:
      runOnce:
        deploy:
          steps:
          - template: templates/deploy-steps.yml
            parameters: { appCatalogUrl: '$(AppCatalogUrl)', scope: 'tenant' }
templates/deploy-steps.ymlYAML
parameters:
  - name: appCatalogUrl
    type: string
  - name: scope
    type: string   # tenant | sitecollection

steps:
- task: DownloadSecureFile@1
  name: cert
  inputs: { secureFile: 'spfx-deploy.pfx' }

- task: NodeTool@0
  inputs: { versionSpec: '22.x' }

- script: npm install -g @pnp/cli-microsoft365
  displayName: 'Install CLI for Microsoft 365'

- script: |
    m365 login --authType certificate --certificateFile "$(cert.secureFilePath)" \
      --password "$(CertPassword)" --appId "$(AppId)" --tenant "$(TenantId)"
    PKG="$(Pipeline.Workspace)/sppkg/$(packageName)"
    if [ "${{ parameters.scope }}" = "tenant" ]; then
      m365 spo app add --filePath "$PKG" --overwrite
      m365 spo app deploy --name "$(packageName)" --skipFeatureDeployment
    else
      m365 spo app add --filePath "$PKG" --appCatalogScope sitecollection --appCatalogUrl "${{ parameters.appCatalogUrl }}" --overwrite
      m365 spo app deploy --name "$(packageName)" --appCatalogScope sitecollection --appCatalogUrl "${{ parameters.appCatalogUrl }}"
    fi
    m365 logout
  displayName: 'Deploy to ${{ parameters.scope }} app catalog'
Pin your tool versions

Pin the CLI version (@pnp/cli-microsoft365@x.y.z) and Node version so a new tool release cannot break your Friday deployment. Use npm ci (not npm install) for reproducible installs from package-lock.json.

#Interview questions

Q1How does the pipeline authenticate to SharePoint without a user?

With an Entra app registration that uses a certificate (stored as a secure file), granted SharePoint application permissions (Sites.FullControl.All, or Sites.Selected on the app catalog). CLI for Microsoft 365 (m365 login --authType certificate) or PnP PowerShell uses it to upload and deploy the package.

Q2Why stamp the solution version in the pipeline?

Every deployment needs a higher solution.version for SharePoint to treat it as an upgrade. Deriving it from the build number guarantees uniqueness and traceability from the deployed app back to the exact pipeline run and commit.

Q3How do you add an approval before production?

Use a deployment job targeting an Azure DevOps Environment (e.g. spfx-prod) that has Approvals and checks configured. The stage waits for an approver before running.
