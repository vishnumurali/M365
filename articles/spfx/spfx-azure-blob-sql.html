SPFx with Azure Blob Storage & Azure SQL – Large Files and Relational Data

Upload large files from SPFx to Blob Storage with short-lived user-delegation SAS issued by an Azure Function, and query Azure SQL through a secure API with managed identity and parameterized queries, with architecture, code and security guidance.

Some data does not belong in SharePoint: huge media or engineering files with special retention, or relational data that already lives in SQL. SPFx can work with both safely, always through a small API you control (see AadHttpClient + Azure Functions).

#Part 1 · Large files to Blob Storage

Function: issue a user-delegation SAS for one blobTypeScript
import { BlobServiceClient, BlobSASPermissions, generateBlobSASQueryParameters, SASProtocol } from '@azure/storage-blob';
import { DefaultAzureCredential } from '@azure/identity';

const account = process.env.STORAGE_ACCOUNT!;
const svc = new BlobServiceClient(`https://${account}.blob.core.windows.net`, new DefaultAzureCredential());

export async function createUploadUrl(userOid: string, fileName: string): Promise<string> {
  if (!/\.(pdf|dwg|mp4|zip)$/i.test(fileName)) throw new Error('File type not allowed');
  const container = 'engineering-drops';
  const blobName = `${userOid}/${Date.now()}-${fileName.replace(/[^\w.\-]/g, '_')}`;
  const starts = new Date(Date.now() - 2 * 60 * 1000);
  const expires = new Date(Date.now() + 15 * 60 * 1000);
  const key = await svc.getUserDelegationKey(starts, expires);         // MI needs "Storage Blob Delegator" + data role
  const sas = generateBlobSASQueryParameters({
    containerName: container, blobName, permissions: BlobSASPermissions.parse('cw'),   // create + write only
    startsOn: starts, expiresOn: expires, protocol: SASProtocol.Https
  }, key, account).toString();
  return `https://${account}.blob.core.windows.net/${container}/${encodeURIComponent(blobName)}?${sas}`;
}
SPFx: upload with progress using the Azure SDK in the browserTypeScript
import { BlockBlobClient } from '@azure/storage-blob';

const { url } = await api.post('/upload-url', { fileName: file.name, size: file.size });
const blob = new BlockBlobClient(url);
await blob.uploadData(file, {
  blockSize: 8 * 1024 * 1024, concurrency: 4,
  blobHTTPHeaders: { blobContentType: file.type },
  onProgress: p => setProgress(Math.round((p.loadedBytes / file.size) * 100))
});

Storage CORS must allow PUT from https://contoso.sharepoint.com. The SAS is write-only, single-blob, short-lived and issued only to authenticated users. Downloads follow the same pattern with read-only SAS.

#Part 2 · Azure SQL through an API

SQL: create a contained user for the Function's managed identitySQL
CREATE USER [fn-deviation-api] FROM EXTERNAL PROVIDER;
ALTER ROLE db_datareader ADD MEMBER [fn-deviation-api];
GRANT EXECUTE ON SCHEMA::api TO [fn-deviation-api];
Function: parameterized query with mssql + managed identityTypeScript
import sql from 'mssql';

const pool = new sql.ConnectionPool({
  server: process.env.SQL_SERVER!, database: process.env.SQL_DB!,
  authentication: { type: 'azure-active-directory-default' },      // managed identity in Azure
  options: { encrypt: true }
}).connect();

export async function searchOrders(customer: string, page: number) {
  const p = await pool;
  const r = await p.request()
    .input('customer', sql.NVarChar(100), `%${customer}%`)
    .input('offset', sql.Int, page * 50)
    .query(`SELECT OrderId, Customer, Total, Status, CreatedOn
            FROM api.Orders WHERE Customer LIKE @customer
            ORDER BY CreatedOn DESC OFFSET @offset ROWS FETCH NEXT 50 ROWS ONLY`);
  return r.recordset;
}
Never build SQL strings from user input

Always use parameters (.input(...)) or stored procedures. The API must also authorize which rows a user may see, for example with SQL row-level security keyed on the caller's oid passed as SESSION_CONTEXT.

#Choosing where data should live

Data Best home
Documents people collaborate on SharePoint libraries
Simple business lists (< few 100k rows) SharePoint lists / Microsoft Lists
Relational, secured business data for apps Dataverse (see SPFx + Dataverse)
Existing line-of-business databases Azure SQL behind an API
High-volume key-value / logs Table Storage (see SPFx + Table Storage)
Very large binaries, media, archives Blob Storage

#Interview questions

Q1Why use a user-delegation SAS instead of an account-key SAS?

A user-delegation SAS is signed with an Entra-issued delegation key obtained by the function's managed identity. No account keys exist in code, the SAS can be scoped to one blob with minimal permissions and a short expiry, and it can be revoked by revoking the delegation keys.

Q2Why shouldn't SPFx connect to Azure SQL directly?

Browsers cannot open TDS connections, and exposing a connection string or credentials to client code is insecure. An API centralizes authentication, authorization, validation and query safety, and can use managed identity.
