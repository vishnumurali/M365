Dataverse Capacity, Service Protection Limits and API Throughput

Understand database, file and log capacity, service protection API limits (requests, execution time, concurrent requests), 429 handling with Retry-After, bulk APIs and designing high-volume integrations that stay within limits.

#Capacity

Capacity Contains Tips
Database Table rows, metadata Archive old data, avoid storing files as text/base64
File File/image columns, attachments, notes attachments Store large documents in SharePoint instead
Log Audit, plug-in traces Retention policies, selective auditing

Capacity is pooled at tenant level (base entitlement + per-licence accruals + add-ons) and reported in the Power Platform admin center.

#Service protection limits

Dataverse protects itself per user (or app user) per web server, within a 5-minute sliding window:

Measure Approximate limit
Number of requests 6,000 per 5 minutes
Combined execution time 20 minutes per 5 minutes
Concurrent requests 52

Exceeding them returns HTTP 429 (Web API) or a FaultException (SDK) with a Retry-After duration. The ServiceClient retries automatically. Custom code must honour Retry-After.

Honour Retry-After with HttpClient (Web API)C#
for (int attempt = 0; attempt < 5; attempt++)
{
    var res = await http.SendAsync(Clone(request));
    if ((int)res.StatusCode != 429) return res;
    var wait = res.Headers.RetryAfter?.Delta ?? TimeSpan.FromSeconds(Math.Pow(2, attempt));
    await Task.Delay(wait);
}

#Designing high-volume integrations

#Interview questions

Q1What happens when an integration exceeds Dataverse service protection limits?

Requests are rejected with 429 Too Many Requests (or an SDK fault) including a Retry-After value. Clients must wait that long and retry. Persistent overload means reducing request rate, batching, or spreading load across app users.

Q2How do you load millions of rows into Dataverse efficiently?

Use bulk operations (CreateMultiple/UpsertMultiple) in batches with controlled parallelism, minimize plug-in and audit overhead (filtering attributes, disable non-essential steps during the load if acceptable), handle 429 Retry-After, and run off-peak. Consider elastic tables for very high-volume event data.
