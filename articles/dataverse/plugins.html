Dataverse Plug-ins – Event Pipeline, Pre/Post Images, Sync vs Async and a Complete C# Example

Write, register and debug plug-ins, covering the event execution pipeline stages (pre-validation, pre-operation, post-operation), IPluginExecutionContext, images, depth checks, throwing user-friendly errors, the Plug-in Registration Tool, tracing and best practices.

A plug-in is a .NET class (IPlugin) that Dataverse runs inside the event pipeline when a message (Create, Update, Delete, Assign, custom API…) is processed. It is the Dataverse equivalent of a classic SharePoint event receiver, with transactional behaviour.

#The event pipeline

Stage Transaction Typical use
Pre-validation (10) Outside Early validation, cancel before locks
Pre-operation (20) Inside Modify the Target (set defaults, compute fields)
Post-operation (40) sync Inside Create related rows; failure rolls back everything
Post-operation async Background (system job) Integrations, slow work, non-critical

#Complete example: validate and stamp a deviation

DeviationPlugin.csC#
using System;
using Microsoft.Xrm.Sdk;

public class DeviationPlugin : IPlugin
{
    public void Execute(IServiceProvider serviceProvider)
    {
        var context = (IPluginExecutionContext)serviceProvider.GetService(typeof(IPluginExecutionContext));
        var tracing = (ITracingService)serviceProvider.GetService(typeof(ITracingService));
        var factory = (IOrganizationServiceFactory)serviceProvider.GetService(typeof(IOrganizationServiceFactory));
        var service = factory.CreateOrganizationService(context.UserId);

        if (context.Depth > 2) return;                                   // guard against recursion
        if (!(context.InputParameters["Target"] is Entity target) || target.LogicalName != "cr8a1_deviation") return;

        tracing.Trace($"{context.MessageName} stage {context.Stage} for {target.Id}");

        // Pre-image holds the values BEFORE the update (registered on the step with alias "pre")
        Entity pre = context.PreEntityImages.Contains("pre") ? context.PreEntityImages["pre"] : null;

        int? severity = target.GetAttributeValue<OptionSetValue>("cr8a1_severity")?.Value
                        ?? pre?.GetAttributeValue<OptionSetValue>("cr8a1_severity")?.Value;
        DateTime? due = target.Contains("cr8a1_duedate") ? target.GetAttributeValue<DateTime?>("cr8a1_duedate")
                                                          : pre?.GetAttributeValue<DateTime?>("cr8a1_duedate");

        // 1) Validation (Pre-operation): Critical needs a due date within 7 days
        if (severity == 100000002 && (!due.HasValue || due.Value > DateTime.UtcNow.AddDays(7)))
            throw new InvalidPluginExecutionException("Critical deviations must have a due date within 7 days.");

        // 2) Stamp values on Create (no extra Update call needed in pre-operation)
        if (context.MessageName == "Create" && !target.Contains("cr8a1_referenceno"))
            target["cr8a1_referenceno"] = $"DEV-{DateTime.UtcNow:yyyy}-{Guid.NewGuid().ToString("N").Substring(0, 6).ToUpper()}";

        // 3) Closed deviations become read-only (except reopen)
        var oldStatus = pre?.GetAttributeValue<OptionSetValue>("statuscode")?.Value;
        var newStatus = target.GetAttributeValue<OptionSetValue>("statuscode")?.Value;
        if (oldStatus == 2 && newStatus != 1 && target.Attributes.Count > 1)
            throw new InvalidPluginExecutionException("This deviation is closed. Reopen it before editing.");
    }
}

#Registering

Filtering attributes

Always set filtering attributes on Update steps so the plug-in runs only when relevant columns change. It is the single best performance optimization.

#Best practices

  • Keep plug-ins fast (2-minute timeout, sandbox isolation). Move slow work to async steps or Azure (Service Bus).
  • Stateless classes: don't store data in fields between executions.
  • Use ITracingService and enable plug-in trace logs during troubleshooting.
  • Check Depth and filtering attributes to avoid infinite loops.
  • Prefer formula columns, business rules or flows for logic that doesn't need transactions.
  • Unit test with FakeXrmEasy or similar.

#Interview questions

Q1What is the difference between pre-operation and post-operation stages?

Pre-operation runs inside the transaction before the core write, so you can modify the Target without another update. Post-operation runs after the write (sync inside the transaction or async afterwards) and is used to act on the saved data, such as creating related records. Any exception in a sync stage rolls back the whole operation.

Q2What are pre- and post-images?

Snapshots of the row's column values before (pre-image) or after (post-image) the operation, registered on the step with chosen columns. They let a plug-in compare old and new values without extra Retrieve calls.

Q3How do you show a friendly error to the user from a plug-in?

Throw InvalidPluginExecutionException("message") in a synchronous stage. The transaction rolls back and the message is shown in the app or API response.
